## 1. Полный доступный корпус Terminal-Bench

Перепись: `data/corpus-census.csv`, одна строка на задачу, генератор
`tools/corpus_census.py`, тесты парсера `tests/test_corpus_census.py` (8/8,
включая сверку с прочитанным вручную `task.toml`).

| корпус | задач | пригодны на стенде | медиана экспертного времени | лимит агента |
|---|---|---|---|---|
| terminal-bench-2.0 | **89** | **89 (100%)** | 1.0 ч (0.08-40) | 900 с (600-12000) |
| terminal-bench-4.0 | 66 | 57 (86%) | 4.0 ч (0.75-24) | 28800 с |

Девять задач terminal-bench-4.0 не запускаются на стенде: восемь требуют

`infeasible_reason`.

**Вывод: terminal-bench-2.0 доступен полностью. Смена бенчмарка не требуется.**

Парсер переписи чинился дважды, оба дефекта - «тихие», дающие правдоподобное
неверное число вместо ошибки: чтение `timeout_sec` из первой попавшейся секции
вместо `[agent]`, и остановка разбора секции на `[` внутри значения
`tags = [...]`, из-за чего экспертное время всех задач terminal-bench-2.0
читалось как отсутствующее. Оба закрыты тестами.

## 2. Расчёт мощности

Полный расчёт: `results/POWER.txt`, генератор `tools/power_requirement.py`.

Тест - точный Макнемара, двусторонний, alpha = 0.05. Информацию несут только
задачи, на которых условия разошлись.

| величина | значение | источник |
|---|---|---|
| минимум дискордантных задач для p < 0.05 | **6** | точный биномиальный расчёт |
| измеренная доля дискордантности (медиана по условиям) | **0.08** | 12 задач, 3 испытания |
| **требуемый размер корпуса** | **72 задачи** | 6 / 0.08 |

Это нижняя граница: она предполагает, что **все** разошедшиеся задачи
разойдутся в одну сторону. Любая задача, разошедшаяся в обратную, поднимает
требование резко.

Предыдущая оценка в 36 задач была занижена вдвое - она исходила из доли
дискордантности 0.17, наблюдавшейся только у одного условия, а не из медианы
по условиям.

**terminal-bench-2.0 (89 задач) покрывает требование в 72 задачи.**

Отдельно измерено: воспроизводимость вердикта одной ячейки между тремя
испытаниями - 54 из 72 (75%). Испытания не заменяют задачи: шум вердикта
одного порядка с искомыми эффектами.

## 3-4. Canonical dataset и словарь данных

`data/canonical-runs.csv` - 225 строк, одна строка = один прогон, ни одной
агрегированной или производной колонки. Генератор
`tools/build_canonical_dataset.py`.

Словарь: `data/DATA-DICTIONARY.md` - определение каждого поля, источник каждого
значения, определения условий (`tail0` и т.д. больше нигде не появляются без
расшифровки), значения `stop_reason`, и явный раздел «известные ограничения».

`stop_reason` **пересчитан из сырых каталогов**, а не скопирован из прежних
строк: прежний флаг таймаута производился детектором, который ловил
конфигурационную строку harbor и давал 54 таймаута там, где их ноль.

Цепочка происхождения любого числа:

```
/opt/runs/<run_id>/                     сырой прогон
  .../sessions/*.jsonl, verifier/reward.txt   сырые измерения
  tools/build_canonical_dataset.py            детерминированная агрегация
  data/canonical-runs.csv                     canonical dataset
  tools/publication_tables.py                 таблицы
```

## 5. Таблицы

`results/TABLES.txt`, генератор `tools/publication_tables.py`.

Заголовок каждой таблицы содержит: экспериментальную единицу, бенчмарк, размер
выборки, число независимых испытаний, модель, способ агрегации, меру разброса,
применённый статистический тест (или явное «не применялся»).

**Доли решённых задач в таблицах отсутствуют намеренно.** На выборке из 12
задач они не обладают мощностью, и ставить их рядом с хорошо определёнными
стоимостными величинами значило бы предлагать читателю взвешивать их одинаково.

### Что показывает Таблица 1 (сокращённо)

Медиана парного отношения к контролю того же испытания, IQR по задачам:

| условие | пик промпта, исп. 1/2/3 | стоимость, исп. 1/2/3 |
|---|---|---|
| State-only | 0.36 / 0.38 / **0.29** | 2.35 / 2.09 / **1.94** |
| State + 2 | 0.63 / 0.57 / 0.50 | 1.84 / 1.57 / 1.13 |
| State + 6 | 0.90 / 0.79 / 0.85 | 1.82 / 1.67 / 1.68 |
| State + transcript | 1.40 / 1.69 / 1.31 | 1.96 / 2.00 / 1.55 |

Единственный результат, воспроизведённый во всех трёх независимых испытаниях:
**чистый SKILL.state сокращает пик промпта примерно втрое и при этом стоит
примерно вдвое дороже контроля.**

Это RQ4 («сокращение токенов не равно сокращению стоимости при кэшировании
префикса») и он единственный, по которому данные позволяют высказаться.

## 6. Механизм: ручная проверка на конкретных прогонах

`results/MECHANISM-fix-git.txt`, генератор `tools/mechanism_ledger.py`.

Вопрос «почему состояние дороже» проверен не корреляцией, а походовым
разбором.

**Пара 1**, задача `fix-git`, испытание 1, **обе** решили задачу:

| | контроль `m-fix-git-baseline-t1-114748-339289` | state-only `m-fix-git-tail0-t1-122726-339289` |
|---|---|---|
| ходов | 10 | 31 |
| cacheRead первый → последний ход | 704 → **6208** | 1728 → **2112** |
| выходных токенов всего | 2 831 | **13 495** |

**Пара 2**, задача `db-wal-recovery`, испытание 1, обе решили:

| | контроль `m-db-wal-recovery-baseline-t1-115010-339289` | state-only `m-db-wal-recovery-tail0-t1-123408-339289` |
|---|---|---|
| ходов | 7 | 13 |
| cacheRead первый → последний | 0 → **4736** | 0 → **2048** |
| выходных токенов | 2 447 | **9 082** |

Механизм читается прямо в данных: у контроля кэшированный префикс **растёт
монотонно** с накоплением диалога, поэтому поздние ходы обслуживаются из кэша.
У state-only префикс **не растёт**, потому что блок состояния переписывается
каждый ход, а переписанный префикс переиспользовать нельзя. Переписывание
оплачивается **выходными** токенами - самым дорогим тарифом.

Обе пары выбраны из 22 пар, где **оба условия решили задачу**, чтобы механизм
не смешивался с разницей в исходе.

Оба прогона независимо пересчитаны из сырых сессий (`tools/verify_run.py`):
все измеренные поля совпали до единицы.
