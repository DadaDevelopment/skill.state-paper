# SPEC: pi-skill-state - плагин SKILL.state для pi

Статус: **дизайн на утверждение. Не реализовано.**
Основания: статья arXiv 2608.26263 (`log/PAPER-skill-state.md`), живой замер
API (`log/E06-context-probe-findings.md`), скилл `ai-agents-architect`.

---

## 1. Understanding

**Что строим.** Расширение pi, реализующее рантайм SKILL.state: модель на шаге
видит спецификацию задачи, структурное состояние и последнее наблюдение;
промежуточные рассуждения и накопленный транскрипт в следующий промпт не
попадают.

**Зачем.** Три эффекта из статьи, за которые стоит платить: ограниченный
промпт при длинном горизонте, устойчивость к мусору в наблюдениях, нулевое
время восстановления при внешнем изменении мира. Плюс наш собственный мотив:
`pi-memory-algorithms` уже содержит все базлайны статьи, кроме самого
SKILL.state - без него сравнение неполное.

**Для кого.** Бенчмарк-прогоны на стандартных агентских бенчах; сравнение с
портированными стратегиями в одном харнессе.

**Ключевые ограничения.**
- Не форкать pi. Только extension API.
- Не терять траекторию: аудит и `/tree` обязаны продолжать работать.
- Один тяжёлый процесс на VM за раз, диск ~3G свободно.
- Слабые модели ломают формат чаще, чем логику (5.7 статьи: 68% - затирание
  ключей, 12% - кривой JSON).

**Явные не-цели.**
- Не мультиагентность (статья сама её не проверяла: конкурентные записи
  требуют семантики разрешения конфликтов в мерж-операторе).
- Не автоматический вывод схемы на лету (раздел 7, случай 1 - там подход
  ломается по построению).
- Не свой бенчмарк. Warehouse из E05 закрыт, дальше только стандартные.

## 3. Решения и почему именно так

### D1. Контекст: чистый режим по умолчанию, гибрид как предохранитель

**Решено:** дефолт - чистый `(P, Sigma, O)`. Дополнительно детектор
отсутствия прогресса: если N ходов подряд состояние не меняется
(`state_patch` пустой или семантически no-op), плагин **эскалирует** -
добавляет хвост последних K сообщений и печатает предупреждение. Если и это не
помогает - останавливает прогон.

**Альтернативы.** (а) Только чистый: честнее к статье, но E06 показал цену
отказа - не деградация, а зацикливание, а у pi своего стопора нет.
(б) Только гибрид: цикл не возникает, но это уже не SKILL.state, и
эксперимент перестаёт мерить то, что заявлено.

**Почему так.** Чистый режим остаётся тем, что измеряется; эскалация - это
не тихий фолбэк, а **громкий отказ с диагностикой** (принцип "agents should
fail loudly" из `ai-agents-architect`). Срабатывание детектора логируется и
попадает в отчёт прогона: если он сработал, прогон помечен как деградировавший,
а не тихо засчитан.

### D2. Схема состояния - из скилла

**Решено:** схема живёт во фронтматтере SKILL.md рядом с инструкциями
(`state_schema`). Нет схемы - плагин не активируется для этой задачи.

**Альтернативы.** (а) Одна универсальная схема кодинг-агента: соблазнительно,
но угадать поля заранее нельзя, а плохая схема = нарушенное условие
достаточности = D1-эскалация на каждом прогоне. (б) Модель выводит схему сама:
раздел 7 статьи прямо называет это случаем, где подход не работает.

**Почему так.** Статья: "схемы пишутся один раз на домен, не на задачу" - для
всех 100 задач InterCode CTF одна схема из 5 полей. У pi скилл **и есть**
домен, и он уже загружается прогрессивным раскрытием. Совпадение идеальное:
скилл несёт и инструкции `P`, и схему `Sigma`.

### D3. Патч - тулом, а не парсингом текста

**Решено:** `registerTool` с typebox-схемой, поля `state_patch` + `action`
(action опционален - у кодинг-агента действие выполняют штатные тулы pi).

**Альтернатива:** fenced JSON из текста, ровно как в Приложении A.4 статьи.

**Почему так.** 12% ошибок слабых моделей в статье - это синтаксис JSON;
схема на стороне провайдера этот класс убирает. Плата: перестаём мерить ровно
ту же величину, что авторы. Компромисс: флаг `--state-patch-mode=tool|text`,
дефолт `tool`, текстовый режим - для верной репликации.

### D4. Владение схемой и валидация - в рантайме

**Решено:** плагин валидирует патч против схемы, мержит с null-deletion,
при невалидном патче - откат и один ретрай с текстом ошибки в наблюдении.

**Почему так.** Прямо из статьи: модель предлагает, рантайм решает; кривой
патч не может испортить `Sigma`. Плюс sharp edge "tool errors not surfaced" -
ошибку возвращаем модели, а не глотаем.

### D5. Персистентность - через `details` tool result

**Решено:** снимок состояния кладём в `details` результата тула; на
`session_start` восстанавливаем прогоном по `ctx.sessionManager.getBranch()`.

**Почему так.** Это штатный механизм pi для состояния расширений
(`docs/extensions.md:1879`) и единственный, который корректно переживает
ветвление `/tree` и `/fork`. Отдельный файл на диске при branching разъедется.

### D6. Аудит бесплатно

**Решено:** ничего специально не делаем. Сессия пишется мимо хука.

**Почему так.** [live] E06: 225 записей на диске при 2 в промпте. Это снимает
ограничение 3 статьи (задачи над траекторией) - и это **отличие нашей
реализации от статьи, которое стоит вынести в текст**: у pi контекст-окно и
журнал сессии разведены, чего у авторского рантайма нет.

## 5. Порядок работ

1. Скелет плагина: `state_patch` тул + хук `context` + детектор прогресса.
2. Микро-задача на 5-10 шагов, три прогона: baseline pi / чистый / гибрид.
   Смотрим ходы, промпт, успех.
3. Только после зелёной микро-задачи - стандартный бенч.
